# 2. Skills are harness-neutral Markdown

- **Status:** Accepted
- **Date:** 2026-08-29

## Context

Day-to-day work here runs in Claude Code. But harnesses change faster than
standards do: a new CLI, a hosted agent, a CI runner, an IDE integration, a
different vendor entirely. If the skill library is written in one product's syntax,
every one of those changes is a migration, and in the meantime the library cannot
be read by the other tools or by a person.

There is also a subtler failure. Skills written against a specific harness drift
toward prompting technique — instructions about how to make *that model* behave —
rather than toward standards, which are the thing worth keeping. The technique is
obsolete within a year. The standard is not.

## Decision

Skills in `skills/` are plain Markdown with YAML frontmatter (`name`,
`description`, optionally `when_to_use`) and contain no harness-specific syntax:
no tool names, no slash-command references, no product-specific tags, no
model-specific prompting.

The test: **a competent engineer with no agent should be able to follow the skill
and produce acceptable work.** If a paragraph only makes sense to a particular
product, it is configuration, and it belongs in the sync script that generates that
product's directory.

Harness-specific affordances — Claude Code slash commands, settings files, hook
configuration — are generated by `scripts/sync-harnesses.sh` into `.claude/` and
are not part of the library.

## Consequences

**Good.** One library serves every harness and every human. Adding a harness is a
function in the sync script. Skills stay readable as onboarding documentation,
which means they get reviewed properly, because a reviewer can tell whether they
are right. The library survives a change of model vendor.

**Bad.** We give up harness-specific power. A product feature that would make a
skill sharper — a structured tool-call contract, a native checklist type — cannot
be used in the library and must be expressed as prose plus a projection. Some
skills are therefore slightly less effective in Claude Code than a bespoke version
would be. We accept that: portability and reviewability are worth more than the
last few percent.

**Also bad.** The rule needs enforcement, or it erodes one convenient exception at
a time. `scripts/validate.py` fails on a denylist of harness-specific
markers, which is crude and will need updating.

## Alternatives considered

**Write for Claude Code, port later.** Rejected: "port later" means the port never
happens, and by the time it is needed the library is thousands of lines of
product-specific text.

**Maintain parallel libraries per harness.** Rejected: they diverge within weeks,
and it triples the review burden for every standards change.

**A structured format — JSON or a DSL — compiled to each harness.** Rejected: it
buys precision we do not need and costs the property we care about most, which is
that a human can read a skill and tell whether it is correct. Markdown is the
lowest common denominator on purpose.
